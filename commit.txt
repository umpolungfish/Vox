Verdict a swept fragment as a fragment, not as an ill-typed function

My kernel audit reported F 4, and the natural reading was that four functions in
mOMonadOS fail to close. They do not. The walk returns two kinds of thing in one
vector: functions descent reached by following the program's own edges, and runs
an in-walk linear sweep guessed at when descent ran out. The report called the
whole vector the trustworthy set.

A swept run is cut wherever the scan happened to stop. Cut there, the piece can
carry a merge whose fork stayed behind in code the scan already left: a merge
with no fork, verdict F. That is true of the fragment and false of the function
it came from, so it must not be counted in the same column.

Walk now says where descent stopped and sweeping began, and the report tallies
the two populations apart. On mOMonadOS the descended functions are F 0, and all
four F are fragments. The ill-typed listing prints descended functions only.

Measured on the way, and worth writing down because it cost four wrong fixes:
descent does not stall at a call that never returns — it follows a call's return
edge. It stops at unconditional terminators, and what follows a jmp is reached
only indirectly. Nothing branches to any swept start, so no reattachment rule
built on reachability can fire; attaching by adjacency instead only glues a
fragment to whichever function happens to precede it in memory, which moves the
F without answering it.

cargo test is green.
